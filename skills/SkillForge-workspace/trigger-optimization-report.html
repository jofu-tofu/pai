SkillForge — Trigger Optimization Report

Status: Automated Optimization Blocked STRUCTURAL LIMITATION

The run_eval.py framework cannot test SkillForge because the skill is already registered in the environment. Two iterations were attempted; both showed 0% recall — a measurement artifact, not a description quality issue.

Why Automated Optimization Failed

The Dual-Registration Problem

run_eval.py works by creating a temporary command file (SkillForge-skill-{uuid}.md) in .claude/commands/ with the description under test. It then runs claude -p with a query and checks whether Claude invokes the temp command.

But the real SkillForge skill is already registered in userSettings. Claude always prefers the real registration over the temp command. Even when Claude correctly routes to SkillForge, the eval marks it as a failure because the tool call targets "SkillForge" not "SkillForge-skill-abc12345".

Verified: Testing with fictional skill names (InventoryTracker, FooBar, BudgetPlanner) that don't match any real skill produced the same 0% recall. This rules out name collision and confirms the mechanism itself is the issue.

Structural Findings

  • run_eval.py is designed for NEW skills — it cannot test skills already registered in userSettings. The temp command approach creates a duplicate that's never preferred.
  • Orphaned temp files pollute routing — 9 leftover SkillForge-skill-*.md files from crashed eval runs were found in .claude/commands/. These create confusing duplicate entries in the skill list. Cleaned up.
  • Anthropic API key required for improve_description.py — the automated improvement step uses the Anthropic SDK directly (not claude -p). Without ANTHROPIC_API_KEY, the optimization loop crashes after iteration 1.
  • Eval set design matters — all 10 should-trigger queries referenced real skill names (Research, ClarityEngine, Obsidian). Even without the dual-registration problem, these queries test meta-skill routing, which is an architecture feature, not a description feature.

Rationale: Phase 1 proves it works well in practice (90.6% pass rate). The automated optimization could not generate a validated improvement due to the structural eval limitation. Changing the description without validated evidence would violate OptimizeDescription's own quality standards.

Fix for Future Optimization

To enable automated optimization of already-registered skills, run_eval.py needs one of:

  1. Temporary skill deregistration — remove the real skill registration during testing, test only with the temp command
  2. Real-skill detection — also check if Claude invokes the real skill name (not just the temp command)
  3. Isolated environment — run claude -p with --skip-user-settings (if available) or in a clean profile
